Marck Beggs Site

Site guide — how to run it, edit it, and what's changed over time.

Separate project from Clay Carson Photography: its own folder (marck-beggs-website), its own GitHub repo, its own Vercel project. Live preview at the Vercel URL — marckbeggs.com's DNS still points at the old Bluehost/WordPress site untouched, and only gets repointed on a deliberate go-live decision.

Your regular workflow

Two different paths depending on what you're doing:

  1. Music and books/writings — anything at all (edit, delete, or add brand new with a cover photo upload) — log into /editor in a browser and do it there. No coding, no terminal. It commits directly to GitHub and the live site rebuilds within about a minute. This is also what Marck's own copy, Editor Guide for Marck.html, walks through in plain language.
  2. Photo collections — editing a collection's title/subtitle or deleting it works the same way through /editor, but adding a brand-new collection is still a manual step for you specifically (see Adding brand-new content) since Marck hasn't needed to add photos himself.

Using the editor

/editor/login asks for an email and password. Clay's login is clayk1959@gmail.com with EDITOR_PASSWORD — the same identity and password as the Clay Carson Photography editor, on purpose, one thing to remember across both sites. Additional users (Marck) go in EDITOR_USERS as name:password lines, one per line, matching the pattern that project's lib/editor-users.ts already used. Neither is stored anywhere in the code — both are env vars. A successful login sets a signed session cookie good for 30 days; no database is involved anywhere in this — the cookie itself is the proof of login, HMAC-signed with that person's own password so it can't be forged without knowing it, and every editor commit records who made it (Editor (name): ...).

From the /editor dashboard, three sections:

SectionWhat you can do today
PhotosEdit a collection's title/subtitle, or delete the whole collection (removes its JSON entry and its entire image folder from the repo in one commit). Adding a brand-new collection is still local-only — see Adding brand-new content.
BooksAdd a brand-new book or anthology with a cover photo upload, edit any field (title, year, publisher, note, buy link, cover) on an existing one, or delete one (also removes its cover image file).
MusicAdd a brand-new release with a cover photo upload and up to 5 streaming-service links, edit any field (including swapping the cover) on an existing release, or delete one (also removes its cover image file). One filled-in link skips straight to that service's mini-player when tapped on the public site; more than one shows a picker.

Every save/add/delete is a real commit straight to GitHub via its Git Data API — there's a short delay (usually under a minute) between clicking Save and the live site actually showing the change, since Vercel has to rebuild first. The editor page itself updates instantly (it shows a "Saved"/"Added [title]" confirmation for 1.4 seconds before collapsing the form, so it's clear which entry actually changed and the layout doesn't jump right as you click the next thing — see V79); a hard refresh of the public page won't show the change until the rebuild finishes. Cover images upload straight from the browser to Vercel Blob storage and get resized server-side (max 1600px, mozjpeg) before landing in the commit — see V77.

Command reference

CommandWhat it does
npm run devStarts the site locally at http://localhost:3000, editor included.
npm run buildProduction build check — mainly for troubleshooting before a push.
npm run lintCode-quality check.
npm startRuns a production build locally.

There's no gallery:sync/save pair like the photo site has — this project is small enough that git commands (git add, git commit, git push) are used directly for anything the editor can't do yet.

Local development

Requires Node.js 20 or newer.

npm install
npm run dev

Then open http://localhost:3000. The editor works locally too, using the same EDITOR_PASSWORD/GITHUB_TOKEN set in .env.local — there's no "dev mode bypass," logging in is required even on your own Mac, and edits made locally still commit for real to GitHub.

Content data files

Everything editable lives in plain JSON under data/, read directly by the page components — no CMS, no database:

FilePowers
data/links.jsonContact email, streaming/store links (Spotify, Apple Music, CD Baby, YouTube).
data/books.jsonEvery book/anthology — title, year, publisher, cover image path, buy link. Each has a stable id the editor uses to target edits/deletes.
data/music-releases.jsonEvery release shown in the Music page's Releases gallery — title, year, credit, cover image, and either 5 streaming-service links or a self-hosted track list (title/note/audio path per track). Each has a stable slug the editor uses to target edits/deletes.
data/photo-collections.jsonEvery photo collection — slug, title, subtitle, cover photo, ordered list of photo basenames.

Images live under public/images/ (books, music, site) and public/audio/ (songs, the Kilty Sue reading). Photo collections live under public/gallery/<slug>/full/ and .../thumbs/ — full-size capped at 3200px, thumbnails at 750px, both mozjpeg — matching the resize rules used on the Carson & Muller photo site.

public/ALF/ is a special case: a straight, unedited mirror of the old Arkansas Literary Forum journal (1999-2008, ~740MB) served as static files at /ALF/..., outside the JSON-driven content system entirely — nothing in data/ describes it, and the editor can't touch it. The landing page at /books/arkansas-literary-forum (a normal page component) is the only styled part; every page under /ALF/ itself is exactly the original 2000s-era HTML, unstyled and not mobile-friendly by design — reformatting it wasn't worth the risk of altering other people's original work.

Adding brand-new content

A new book or music release

Fully self-serve through /editor now — click + Add a release or + Add a book at the top of the Music or Writings editor. Choose a cover photo from your computer, fill in the fields, and save. The cover uploads directly (no size limit worth worrying about), gets resized automatically, and the whole thing — image plus the new entry — commits and goes live in one shot, same as any other editor save.

For music releases specifically: fill in one streaming-service URL and the release plays as a direct mini-player when tapped, same as the dog gods 2008 album; fill in more than one and tapping shows the pick-a-service screen instead, same as every multi-service release. Leave a service blank to skip it.

A new photo collection

Still a step Clay does locally rather than through the editor (Marck hasn't needed this) — run node scripts/add-gallery-collection.mjs "<Title>" "<source folder>", which resizes every photo in that folder to the same rules as everything else (full-size ≤3200px, thumbnail ≤750px, both mozjpeg) into public/gallery/<slug>/full/ and .../thumbs/ and adds the matching entry to data/photo-collections.json automatically. Then just git add -A && git commit -m "..." && git push. The editor can edit that collection's title/subtitle or delete it afterward, same as always.

Architecture & external services

Next.js (App Router) on Vercel, deployed from GitHub — no database, no third-party accounts beyond GitHub and Vercel themselves.

PieceRole
GitHub repo clayk1959-droid/marck-beggs-websiteSource of truth for everything — code, content JSON, and images all live in git.
Vercel project marck-beggs-websiteBuilds and hosts the live site; auto-deploys on every push to main.
lib/github-commit.tsThe editor's only way of changing anything — talks directly to GitHub's low-level Git Data API (blobs → tree → commit → update ref) so an edit is a real, ordinary git commit, not a side-channel database write. Retries automatically if two edits land at nearly the same moment.
lib/editor-auth.ts / lib/session-cookie.tsPassword check + signed session cookie. No database — the password itself is the HMAC signing key, so nothing needs to be "revoked" anywhere except changing the env var.

Env vars involved: EDITOR_PASSWORD, GITHUB_TOKEN (classic personal access token, repo scope — fine-grained tokens have had unreliable support for the Git Data API endpoints this needs), GITHUB_REPO, GITHUB_BRANCH. Set in both .env.local (local dev) and the Vercel project's production environment variables.

Deploying

Push to main and Vercel builds and deploys automatically — usually live within a minute or two. No manual deploy step needed for either code changes or editor-driven content commits.

marckbeggs.com's domain, DNS, and the old WordPress hosting are all the same Bluehost account (checked via public WHOIS/DNS, no login needed) — the domain registration itself expires November 1, 2026, worth confirming auto-renew is on independent of this rebuild. When it's time to go live, the DNS records get repointed at Vercel from inside that same Bluehost account — no nameserver change or account transfer required.
