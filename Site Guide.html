Your regular workflow

Two different paths depending on what you're doing:

  1. Editing or removing something that already exists (a collection's title, a book's buy link, a music art label, deleting any of the three) — log into /editor in a browser and do it there. No coding, no terminal. It commits directly to GitHub and the live site rebuilds within about a minute.
  2. Adding something brand new (a new photo collection, a new book with its cover, new music art) — the editor can't do this yet (see Adding brand-new content), so it's a manual step: drop the files in, edit the matching JSON file, commit, push.

Using the editor

/editor/login asks for a password (EDITOR_PASSWORD, set as an env var — not stored anywhere in the code). A successful login sets a signed session cookie good for 30 days; no database is involved anywhere in this — the cookie itself is the proof of login, HMAC-signed with the password so it can't be forged without knowing it.

From the /editor dashboard, three sections:

SectionWhat you can do today
PhotosEdit a collection's title/subtitle, or delete the whole collection (removes its JSON entry and its entire image folder from the repo in one commit).
BooksEdit any field (title, year, publisher, note, buy link) on an existing book or anthology, or delete one (also removes its cover image file).
MusicEdit a cover-art image's label, or delete it (also removes the image file).

Every save/delete is a real commit straight to GitHub via its Git Data API — there's a short delay (usually under a minute) between clicking Save and the live site actually showing the change, since Vercel has to rebuild first. The editor page itself updates instantly; a hard refresh of the public page won't show the change until the rebuild finishes.

Command reference

CommandWhat it does
npm run devStarts the site locally at http://localhost:3000, editor included.
npm run buildProduction build check — mainly for troubleshooting before a push.
npm run lintCode-quality check.
npm startRuns a production build locally.

There's no gallery:sync/save pair like the photo site has — this project is small enough that git commands (git add, git commit, git push) are used directly for anything the editor can't do yet.

Local development

Requires Node.js 20 or newer.

npm install
npm run dev

Then open http://localhost:3000. The editor works locally too, using the same EDITOR_PASSWORD/GITHUB_TOKEN set in .env.local — there's no "dev mode bypass," logging in is required even on your own Mac, and edits made locally still commit for real to GitHub.

Content data files

Everything editable lives in plain JSON under data/, read directly by the page components — no CMS, no database:

FilePowers
data/links.jsonContact email, streaming/store links (Spotify, Apple Music, CD Baby, YouTube).
data/books.jsonEvery book/anthology — title, year, publisher, cover image path, buy link. Each has a stable id the editor uses to target edits/deletes.
data/tracks.jsonSong titles, notes, and audio file paths for the Music page's track list.
data/music-art.jsonCover-art images shown on the Music page, each with an optional label.
data/photo-collections.jsonEvery photo collection — slug, title, subtitle, cover photo, ordered list of photo basenames.

Images live under public/images/ (books, music, site) and public/audio/ (songs, the Kilty Sue reading). Photo collections live under public/gallery/<slug>/full/ and .../thumbs/ — full-size capped at 3200px, thumbnails at 750px, both mozjpeg — matching the resize rules used on the Carson & Muller photo site.

Adding brand-new content (until upload support ships)

The editor can edit/delete what's already there, but can't yet accept a file upload or resize an image — that's the next planned phase. Until then, adding something new is a manual step:

A new photo collection

  1. Resize the photos yourself (or ask for a quick one-off script run) to roughly the same rules as everything else: full-size ≤3200px, thumbnail ≤750px, both JPEG.
  2. Create public/gallery/<new-slug>/full/ and .../thumbs/, drop the matching files into each.
  3. Add a new entry to data/photo-collections.json (slug, title, subtitle, cover, ordered photo list).
  4. git add -A && git commit -m "..." && git push.

A new book or music art image

Same idea: drop the image into public/images/books/ or public/images/music/, add the matching entry to data/books.json or data/music-art.json (give a book a unique id), commit, push.

Architecture & external services

Next.js (App Router) on Vercel, deployed from GitHub — no database, no third-party accounts beyond GitHub and Vercel themselves.

PieceRole
GitHub repo clayk1959-droid/marck-beggs-websiteSource of truth for everything — code, content JSON, and images all live in git.
Vercel project marck-beggs-websiteBuilds and hosts the live site; auto-deploys on every push to main.
lib/github-commit.tsThe editor's only way of changing anything — talks directly to GitHub's low-level Git Data API (blobs → tree → commit → update ref) so an edit is a real, ordinary git commit, not a side-channel database write. Retries automatically if two edits land at nearly the same moment.
lib/editor-auth.ts / lib/session-cookie.tsPassword check + signed session cookie. No database — the password itself is the HMAC signing key, so nothing needs to be "revoked" anywhere except changing the env var.

Env vars involved: EDITOR_PASSWORD, GITHUB_TOKEN (classic personal access token, repo scope — fine-grained tokens have had unreliable support for the Git Data API endpoints this needs), GITHUB_REPO, GITHUB_BRANCH. Set in both .env.local (local dev) and the Vercel project's production environment variables.

Deploying

Push to main and Vercel builds and deploys automatically — usually live within a minute or two. No manual deploy step needed for either code changes or editor-driven content commits.

marckbeggs.com's domain, DNS, and the old WordPress hosting are all the same Bluehost account (checked via public WHOIS/DNS, no login needed) — the domain registration itself expires November 1, 2026, worth confirming auto-renew is on independent of this rebuild. When it's time to go live, the DNS records get repointed at Vercel from inside that same Bluehost account — no nameserver change or account transfer required.
